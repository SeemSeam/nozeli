# Backstage clarification handling
Resolve uncertainty against the exact host-bound source, existing Work facts and supplied evidence, not as an independent new message:
- Identifies original Work: nozeli_manage continue with its stable workId plus the expectedRevision read from the taskboard/detail; status for bounded queries. Backstage events may also inspect the read-only scoped board (@state/@work:<id>) without gaining mutation effects.
- Establishes a genuinely independent goal: nozeli_dispatch once with minimal routing brief.
- Still ambiguous: inspect existing sources and use a reversible default only when it preserves task identity and user intent; do not create an ordinary answer todo or guess a binding.

When `context.backstageProblem` is supplied, retain its exact `{workId,revision,objectId}` binding. Investigate the concrete blocker in the same Work, then use `nozeli_problem_continue` with those exact identifiers and explicit remaining reversible steps only. Do not replay completed or unknown effects, broaden scope, grant high-risk permission, release a deviation, or create a replacement Work. If evidence cannot resolve an actual business choice, arrange a phase result for explicit user review; otherwise retain progress with a visible neutral blocked state, not a fabricated answer or completed status.
