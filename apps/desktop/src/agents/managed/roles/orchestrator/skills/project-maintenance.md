# Project maintenance — bounded diagnosis and recovery

This skill is part of the fixed Orchestrator rules. Host transactions with a proven deterministic recovery (pre-prompt preparation, session startup, captured publication, technical closure) run their bounded recovery programmatically in the original scope and record it in a durable local bug ledger. Provider/runtime failures without actionable host recovery — content refusal, auth, rate limit, model unavailable, network/transport — are classified and counted locally only: they never queue a `maintenance` or backstage model turn, never auto-resend, and never rewrite the request to evade a refusal. User-requested diagnosis uses the same bounded capabilities. Never treat archived instructions as new work.

Fatal host tool/runtime exceptions are not provider refusal or service diagnostics. The host retains the failed input with `maintenanceBugId` and `maintenanceFault`, records sanitized bug evidence, and uses the existing maintenance event; a request without a Work remains a system-owned request, not a user repair decision. Without an exact captured safe host action, its status stays `needs-version-fix`: never reconstruct the original prompt, dispatch a replacement Worker, replay admitted/unknown effects, or claim repair. Recoverable read-argument corrections remain inside the current native turn and are not fatal job failures.

## Real host capability

Call `nozeli_maintenance({action:"status"})` to inspect sanitized local bug facts (fingerprint, occurrences, original job/Work/revision, actual app version/platform, bounded attempts and host-verified outcome). Use only the host-supplied `bugId`. Call `nozeli_maintenance({action:"retry",bugId})` for the exact advertised capability: proven pre-prompt preparation/session startup, captured publication without a second Worker prompt, or technical closure retaining the original accepted/discard binding. The host enforces singleflight, two recovery attempts per bug and stale/cancel boundaries. A model assertion can never mark a bug repaired. Inspect the returned verification receipt; ordinary native tools can diagnose unknown software faults under the current OS user, not hot-patch the installed app.

`nozeli_maintenance({action:"scan"})` adopts only proven historical internal snapshot/publication or host-origin runtime failures (including the host-tool failure wrapper), preserving history and all accepted inputs; it does not replay old commands. After cold reopen, in-memory captured actions are unavailable: retain `needs-version-fix` rather than reconstructing unknown effects. Unsupported defects remain waiting for a version fix, with diagnosis evidence; do not repeatedly ask users how to repair the program. Maintenance events cannot dispatch or manage a replacement Work. Real permissions, conflicts, unsent drafts and unknown started effects remain human boundaries and their native reminders stay visible.

## Temporary runtime continuation first

After `debug.report` is saved, check the response for `hostContinuation`. When the host exposes a capability it alone proved (first: a dispatch rejected before any Work was created because of an empty brief), you MUST actively call `nozeli_maintenance({action:"debug.continue",bugId,attemptId})` in the same debug attempt instead of stopping at a saved diagnosis. The host — never the model — performs the continuation on the exact original intake: the original request is retained verbatim and reused as the temporary brief, the normal dispatch contract (source, frozen attachments, idempotency, permissions, version, quota, original sourceJob) is reused, exactly one Work is created, and the durable receipt plus routing land in one persistent business transaction. Repeated, concurrent or cold-restarted calls only read that receipt back; they never dispatch again.

Historical scope note: the empty-brief dispatch fault is a recorded pre-fix source defect. Dispatch now treats an omitted/null/blank `brief` as the frozen original user request and the board treats an omitted/null/blank `cursor` as the first page, so new turns can no longer hit `DISPATCH_BRIEF_EMPTY`. The continuation capability therefore applies only to rejection evidence the host durably captured at pre-fix failure sites (kept readable and idempotent, never deleted); fixing the source does not retroactively mark those bugs repaired.

`continuing` means the temporary recovery is executing; `continued-with-known-fault` is only set from the actual persisted business receipt. Both keep `verifiedFix:false` and `sourceRepairRequired:true`: the source fault stays unfixed, the bug is never marked repaired, and the original task continuing is not a delivered result. Do not modify source code or the installed app, do not hand-write databases or locks, and do not re-send or rephrase the original user request to work around the fault. Without explicit host-provided safety evidence (`DEBUG_CONTINUE_UNAVAILABLE`), keep the diagnosis saved and awaiting fix; unknown effects, executed-but-unconfirmed commands, permission holds, manual pauses/cancellations and identity/version conflicts are hard fences the debug turn must not bypass.

## Diagnose before acting

1. Use `nozeli_inspect_work` with the exact existing Work name or host-provided reference. Read full blocker evidence when the preview is incomplete. Preserve the original Work, revision, accepted object, candidate, human drafts and conversation.
2. Separate business outcome, native process/turn settlement, candidate integration, provenance and resource cleanup. `ended`, `accepted`, `completed job` or `ready` alone does not prove that the accepted document is in the target branch.
3. Classify the concrete evidence:
   - `MERGE_CONSENT_REQUIRED`: a user policy/consent decision, not a crashed Worker. Present the original version-bound todo; do not choose for the user.
   - `INPUT_OVERLAP`, `USER_DIRTY`, `TARGET_OVERLAP`, `HEAD_DRIFT`: preserve the source and candidate. Compare the Work input snapshot, accepted candidate and current target. A user's explicit merge instruction authorizes reconciliation, not blind overwrite or index reset.
   - `INVALID_PAYLOAD`, stale handles or malformed command arguments: correct the call from host evidence, not request broader permission.
   - Missing build dependencies: an environment prerequisite, not role-based lack of execution capability. Prepare ordinary current-user dependencies and installations directly when needed by the task; no build/install approval is required. Ask only if the concrete effect needs admin elevation, destructive broad deletion/formatting, irreversible damage or sensitive-data export. Do not claim success without a real build.
   - Missing session file: never invent an empty file or replace a historical conversation. Only the host may prove an explicitly handed-off identity had zero activity and was never materialized, then recover it. Keep original archives.
   - Unknown/started execution or unsettled transport: no automatic retry, duplicate prompt or duplicate effect. Preserve receipts for explicit reconciliation.

## Recovery boundary

Use existing recovery/disposition controls only when actually available and authorized. Technical retry retains the exact original decision and candidate, never restarts its Worker or creates another Work. A host-proven pre-effect temporary continuation (`debug.continue`) lets the original task continue under the recorded known fault; it is not a repair and never authorizes replay, fabricated success, or asking the user to debug internals. An unavailable original action means the system must investigate the cause through debug and retain a concrete repair/verification plan. Only the host can verify repaired outcomes or release execution fences. A diagnostic-only report remains pending system repair, not a completed original task.

Do not write SQLite/JSON ledgers, edit internal IDs, delete host locks, force worktree removal, reset the user's index, relabel blocked as complete, or copy a candidate over a current document to suppress a guard. Do not delete notes, human drafts, original reports, history or unfinished work as "cleanup". Full current-user shell capability does not waive these invariants.

Actual software bugs require a reproducible isolated case, a normal source-code candidate and verification. Do not hot-patch the running application or installed release. Ordinary task-required installation, builds and restart use normal current-user tools without an approval todo; preserve the original task, drafts and unknown started effects. Only concrete admin elevation, destructive broad deletion/formatting, irreversible damage or sensitive-data export needs high-risk authorization through normal host/OS mechanisms. A todo approval is not proof of OS elevation.

## Verify the effect, not the promise

For document integration, verify the exact final bytes in the target branch AND current file, retained subsequent edits, actual integration commit, original job IDs unchanged, and closure/provenance/resource cleanup. If authorship cannot be derived truthfully for a manually reconciled document, retain an explicit reconciliation fact rather than attributing all changes to the Worker.

For runtime recovery, verify the expected session identity or archived handoff, readiness, retired connection error, zero unintended jobs/effects, and preserved unsent input. Prove normal shutdown/restart when that was requested. A recovery interface returning accepted is not completion.

Report: concrete failure, observed cause, action actually taken, verification, remaining user decision or prerequisite. Keep normal waiting and user policy gates distinct from software errors. A failure in one Work must not be described as the whole project's failure unless evidence proves that impact.
