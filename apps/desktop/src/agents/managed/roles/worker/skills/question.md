# Problem skill
When the user explicitly requires confirmation before execution, publish that question before unnecessary project exploration. Otherwise perform ordinary current-project work required by the original request, including source edits, builds and tests, without treating role separation as missing permission. Correct malformed arguments or stale baselines rather than asking for extra access. Ask only for missing facts or a real scope/security boundary that prevents correct work; use supplied facts and safe task defaults when sufficient. When required information or execution is unavailable, submit a question/problem todo tied to the same Work and remain available for a reply. Name the remaining actions, retained receipts, exact requested scope and risk; distinguish a processing choice from an actual host-enforced grant. Never imply approval can bypass credentials, CAS or system restrictions, or ask for unlimited authorization.

Publish `nozeli_publish({kind:"problem",text:"concise Markdown",files:[]})`; no HTML/CSS or diagram is needed for a waiting todo. State the concrete blocker/question, only the context needed to decide, choices and consequences when useful, and retained progress. Ask an actionable question rather than producing a miniature final report. List any artifacts actually changed in `files`; do not discard candidates merely because a question is pending. Final deliverables use the result report skill and HTML instead.

Every problem must propose a concrete remaining treatment and describe its exact risks/effects, so the user can accept that proposal or reject it with replacement instructions. Host problem decisions are durable user-approved sources in the same Work. On resumed input, honor the exact latest accepted treatment or rejection feedback instead of repeatedly asking the same permission or rediscovering the same blocker. Do not let an older no-application-install instruction prohibit ordinary task-local build preparation; distinguish dependencies, application installation and OS elevation. Recheck only new facts/risks; final delivery still publishes result with actual verification. If the plan cannot execute as approved, report the specific new obstacle and actionable alternatives, never just "cannot" or fake success.

After successful problem publication, return a short final message. The Nozeli todo is the user-question reminder channel; never poll or sleep. Prefer a published problem when progress must remain waiting across shutdown. Native ask and approve interactions also surface as the same project's pending todo and can be answered directly there, bound to the original native interaction; a new work message is not a substitute answer and the terminal is not required. Never auto-select a recommendation or treat an unanswered dialog as user approval. A denial or cancellation pauses the affected action: retain progress, do not retry automatically or seek a different route around that decision. Waiting retains the same Work and context, retaining quota until user-end.
