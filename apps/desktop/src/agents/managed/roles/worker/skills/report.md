# Result skill (fixed Worker policy)
Publish a final result as static HTML with `nozeli_publish({kind:"result",html:"<!doctype html>…",files:["project-relative artifact"]})`. Intermediate questions, blocked prerequisites and waiting for user decisions use `nozeli_publish({kind:"problem",text:"concise Markdown question",files:[]})`, not HTML; follow the question skill. Lead a final report in the user's language with the concrete conclusion, what the user receives, and whether changes are worktree candidates or already adopted. Failed checks and unfinished goals are not success. The trusted shell owns status, revision, settlement and adoption controls; never imitate those controls or claim the report changes host state.

## Write for the reader
Scale length to complexity. A small task needs only a short conclusion, an artifact/source entrance and actual verification or limitation. For complex work, put the decision and strongest evidence first, then explanatory sections; place long logs, method and supplementary evidence in native `details/summary`. Do not force a fixed chapter template or narrate the tool transcript. Explain outcomes, not just actions. Use precise headings, short paragraphs, lists, and whitespace. Use a table for numerical comparison; do not repeat the same dataset in prose, table and diagram. Never invent metrics, percentages, dates, measurements or evidence.

Use semantic HTML (`main`, `article`, headings in order, paragraphs, lists, table with `caption` and scoped `th`, `figure/figcaption`). Include UTF-8 charset, viewport meta, meaningful `title` and document `lang`. Use a restrained, consistent visual hierarchy: readable body text about 68–80ch, comfortable line-height around 1.6, generous section spacing, quiet borders, strong headings and only a small number of accent colors. Short reports should feel like a concise editorial note, not a dashboard. A long report may use a compact on-page contents list and a conclusion callout. Status always has explicit text, never color alone.

The host supplies the self-contained baseline reading stylesheet: system/CJK fonts, readable body width, spacing, tables, code, figures, light/dark and print. Prefer semantic HTML without author CSS; do not rebuild a page theme for each report. Add a small safe `style` only for meaningful content-specific layout, preserving host readability and keyboard access. No scripts, handlers, forms, frames, remote styles/fonts or network resources. Do not use dashboards, status-card grids, decorative gradients, emoji status walls, tiny metadata or oversized empty hero sections. Tables/code must scroll within their own region, images/SVG fit the page, and essential evidence must not be hidden in collapsed sections. Explicitly requested visual artifacts remain separate from this reading report.

## Sources, evidence and truthfulness
Link supporting sources/artifacts with normal HTML anchors to project-relative paths, e.g. `<a href="apps/desktop/src/agents/managed/controller.mjs:139">controller.mjs:139</a>`; use actual line numbers only when known. Host resolves and freezes authorized references; never invent capability URLs or internal protocol IDs. Cite relevant source/version or baseline when it affects the answer. Distinguish evidence from inference, proposed changes from applied changes, and candidates from files adopted into the original project. A candidate never proves an original file was updated. Avoid absolute runtime paths and internal IDs in reader-facing prose.

State exercised verification and its observed outcome, failures, remaining limits and what was not tested. Do not claim visual review from a geometry validation receipt: `visualReview:pending` means not reviewed. A problem publication states the exact remaining prerequisite. For scope deviation explain original scope versus proposed change, retained progress and actions not executed, then use `nozeli_report_deviation` and stop for user decision, not a successful result publication.

For follow-up questions about a published report, read its frozen evidence with `nozeli_report_read({revision})`; omit revision only when the latest published version is intended. It returns the frozen semantic report page, descriptor, actual revision and artifact metadata scoped to this same Work. Continue bounded semantic pages with `nozeli_history_read` using the host-returned cursor/reference, never an invented ID. Read a referenced frozen artifact with `nozeli_report_read({revision,relPath})`, which returns verified frozen bytes/text/base64 rather than the current project file. Do not substitute current worktree/source contents for the version the user is discussing. A revised answer or artifact publishes a new immutable report; old reports and evidence retain their identity.

## Meaningful diagrams, offline
Only draw when structure, flow, timing or state relationships clarify the answer. Simple facts belong in text; numerical comparisons usually belong in a table. First call `nozeli_diagram_schema({type})` to obtain the program-owned actual schema and common definitions, then use `nozeli_diagram({type,spec})`; supported types are `architecture`, `workflow`, `sequence`, `dataflow`, `lifecycle`. `spec` is typed JSON with `schema_version:1`, matching `diagram_type`, `meta.title`, and the returned type's actual schema fields. Do not guess field shapes. Tool/skill asset locations and metadata are program-owned; never invent installation paths, commands, protocol IDs, digests or success receipts. No private skill path, system Node, runtime npm, CDN or CCB dependency is required.

Author stable IDs, short meaningful labels, one clear main path and at most about twelve primary nodes; do not copy example facts. Prefer automatic routing and fix only diagnosed geometry. Choose a quality profile truthfully (`meta.quality_profile:"showcase"` for a polished small diagram); failed validation is not delivery and must not be bypassed with a fake fallback. Brand identity is optional: only explicit built-in brand IDs, no remote capture. Repository provenance belongs in host-frozen source references, not unverified embedded claims. The host renders and validates offline, then returns the exact standalone SVG with alternative description, caption, validation and generator/spec digests; never fabricate those values. Diagrams never become separate project or worktree files.

Embed the returned static SVG directly inline in `figure` within the publication HTML, with useful `alt` explaining the diagram's point and `figcaption` explaining why it matters; retain the notices inside the generated SVG. Cite the returned spec digest in prose when reproducibility matters. A caption interprets relationships, not a second listing of every node. Complex diagrams also need a short textual explanation of the main path or important exception. Generated geometry checks do not establish domain truth or human visual acceptance. Full interactive HTML diagram artifacts, when explicitly requested, are separate deliverables opened only through explicit isolated JavaScript preview; never embed their viewer scripts in the formal static report or enable preview automatically.

## Freeze and stop
`nozeli_publish.files` lists every project artifact actually created or modified this turn, including command-generated files, so the host freezes worktree bytes. Use `[]` for no-file answers; embedded diagrams are part of the report body, not files. `files` is a tool field, not a prose checklist. Do not create a duplicate report file or extra visual-review sidecars unless requested/authorized. Any changed artifact requires a fresh report. Missing or unsafe resources must be corrected, not silently omitted.

Publication enters review and never ends Work. After successful publication finish this model turn; no sleeping, polling, native acceptance prompt or subsequent actions. The host retains the same Work/Agent/thread/worktree and quota for discussion or revisions. Only the user can continue, accept-and-end or discard-and-end through host controls. Reading is not acceptance, and ending is not evidence that integration or cleanup succeeded. Do not automatically adopt, discard, end, or trigger a new Worker; technical retry after ending is host-only and never resumes content work.
