# 简洁项目生命周期、自动恢复与初始化

Date: 2026-11-08
Status: **源码已实施；独立Reviewer最终代码审阅无具体阻断；Linux真实Electron/Pi限定验收通过。** 未安装、未提交、未重置或解锁用户日常项目；Windows/macOS与付费模型理解质量未验。
Plan Tree: [项目设计入口](plantree/README.md)

## 1. 用户方向与现有反例

用户要求设计简洁稳定，不为每种异常建设复杂修复流程。程序和Orchestrator自动完成能确定的恢复；无法可靠恢复时允许明确完全重置，牺牲部分Nozeli信息。项目首次建立时由Orchestrator梳理文件、建立项目理解与初始化流程。

已证故障见[打开故障分析](project-open-failure-analysis.md)：干净网页关闭要写视图状态，remove围栏却拒绝该写入，失败围栏跨重启阻断打开，错误细节丢失。重设计必须消除此循环，不能仅扩大异常白名单或手删围栏。

## 2. 最小结构

保留一个宿主项目生命周期协调者，复用当前项目库/实例身份/受管进程清单/操作回执。Orchestrator沿现有Pi角色、工具和串行事件接入，不新增恢复Agent、第二任务表、调度器或记忆runtime。

### 固定流程优先Skill（2026-11-08用户追加）

固定的模型工作方法通过Pi原生目录式`SKILL.md`固化、按需加载，不在角色system、事件正文和每轮上下文中重复注入。优先沿[既有技能设计](role-memory-skills-design.md)接线，不建立第二技能加载器。此项是后续实施约束，不表示当前原生skill迁移已经完成；前述Reviewer结论仅覆盖追加前的设计范围。

|内容|承载方式|
|---|---|
|项目初始化、文件理解、项目地图维护|项目初始化skill：读取有界清单/原文、标覆盖、更新同一Plantree主题|
|故障分析、选择支持的恢复动作、核对实际回执|项目诊断skill：有界事实→判断→调用宿主能力→核验；失败给重置建议，不自行删除|
|报告、材料读取、记忆检索与任务续接方法|复用已有角色skill，按职责归并，不为每个错误码再建一个skill|
|身份、冻结/停稳、数据库/删除、CAS、预算和重试次数|宿主程序硬约束；不依赖模型有没有读取skill|
|常驻输入|最小角色契约、真实工具定义、skill短目录；只保留必要强制边界|
|每次事件|实际用户原文或事件事实、稳定身份和材料引用；不粘贴skill全文，不伪装用户指令|

宿主按已知初始化/诊断事件选择适用skill标识，复用Pi渐进读取；普通任务由角色按需发现。需要固定流程而未完成技能读取时，不应声称按该流程完成；同一正文不得经rolePrompt、eventSkill、native skill多路重复交付。版本/来源记录沿既有绑定与Pi历史，不再逐轮补发全文；普通会话不自动加载全部技能。

技能目录只加载受管角色包，不能自动继承项目文件/个人目录中发现的任意指令；skill内容不授予删除、跨实例写入或业务授权。初始化数据预算和只读工具集由宿主限制，项目正文按数据读取，不能变成可信skill。正式切换时迁移所有消费者并删除重复注入路径，不长期双轨。

验收增加一条集成检查：实际Pi会话能发现并读取所选skill，执行流程可追溯；普通请求不附初始化/诊断全文，后续轮次不重复交付同一规则；没有模型/未加载skill时本地打开和程序安全门仍成立。模型是否正确使用skill与宿主安全分别核验。

UI只呈现：可用、处理中、需要重置/人工处理。内部仍保留必要阶段回执用于崩溃核查，但不把每阶段做成用户工作流。业务任务暂停、审阅与未知执行事实不折叠为已完成。

## 3. 自动恢复与重置兜底

- 程序先做确定性核查：身份/目录、当前操作与进程、数据库回执、布局/缓存可重建性。能证明无损安全时自动重连/重建派生视图/核查已停稳旧操作，不反复要求用户按多个恢复按钮。
- 非确定问题给Orchestrator一份有界故障事实及只读诊断工具：判断是否为已支持恢复能力，调用宿主实际能力并核验回执。模型不能自己删库、删锁、改安装代码或把解释标为已修复。
- 自动恢复只运行一个有界周期，遇相同无变化故障不循环派工/无限重试。持久故障与能力回执去重；模型不可用时程序判断/本地阅读仍可工作，不让打开项目依赖LLM在线。
- 任务结果/历史未知时不重放原任务、不声称完成；但不阻止用户明确丢弃Nozeli状态，也不要求逐个采用/丢弃Work才能完全重置。真正阻止删除的是活跃写入者未停稳、删除归属不明或存储关闭不可靠；外部命令效果不能靠重置撤销。
- 不可靠恢复时显示一个主操作“完全重置Nozeli状态并重新打开”，说明损失范围。另有取消/保留现状及按需导出，不设计多层手工修复迷宫。真实目录权限/磁盘不可写/外部进程占用等重置解决不了的原因直接说明，避免承诺重置万能。

## 4. 保存关闭与丢弃重置分离

普通关闭/切换：保存实际未保存内容，保存失败保留现场；视图/缓存故障不能冒充正文丢失。允许本次真实flush owner完成必要持久化，拒绝新业务写入。

完全重置：确认丢弃后冻结新写入→停止并核验自有任务/终端、等待在途操作→关闭DB/销毁旧内容面（不要求保存将丢弃的视图/草稿）→清除归属确认的Nozeli项目状态→发布新实例→打开并重新初始化。旧回调按旧实例拒绝。不能为了丢弃状态跳过进程/路径所有权检查。

重置必须能从已被围栏阻断的项目直接进入，不要求先打开、保存或修复原操作成功。协调者接管同实例已停止/无在途工作的旧操作，保留最小回执后进入丢弃路径；旧操作仍活跃则先停稳，不并发清理。现有preview的assertActive和普通close不能直接复用作此路径前提，这属于待实现的新宿主能力。

清除该根目录各代Nozeli任务、会话、记忆、批注、未发送/未保存副本、布局/缓存、恢复区及受管候选；保留实际项目文件、用户Git、全局模型/账号和其他项目。未采用候选/草稿会失去，接受该损失不意味着删除原正文或未知外部目录。旧恢复档案不得默认重新导入污染新实例；仅保留最小无正文技术回执。

中断后只做一轮有界宿主核查：已确认归属且已不存在的目标视为清除完成；原确认范围内、写入者已停稳的剩余目标可按回执继续清理。所有权变化、未知写入者或存储关闭不可靠则结束为准确阻断，不无限处理中，不重放业务效果。现有permanentReset对未完成操作仅报PROJECT_RESET_PENDING，安全完成能力尚需实现；不建设逐场景恢复框架。

允许丢弃的是已确认范围内的Nozeli资料，不是“恢复工具可自动恢复任意外部效果”。无法证明写入者已停止或外部目录归属时，提示明确的关闭其他实例/恢复磁盘等前提；不能强删未知进程、用户Git或外部资源。安全前提不成立不继续重置，不为此增加多层模型审批。

## 5. 首次项目初始化

程序初始化和语义初始化分离；本地阅读/编辑不依赖Orchestrator成功。

1. 宿主识别新项目/新实例，创建最小受管目录和身份，获取有界文件清单。既有项目不因每次打开重复初始化；重置后视为新实例。
2. 已有可用AI配置且项目启用AI时，新项目自动触发一次“整理项目资料”，沿现有项目数据范围和模型选择，不新增每次初始化审批。可取消/稍后继续；未配置或用户禁用AI时显示待整理，本地阅读不受影响。初始化不额外读取账号配置、秘密文件或发送无界项目全文。
3. 宿主实际限制一次遍历条目/耗时、读取字节和模型/工具工作额度，不只是分页。默认普通项目文本，排除.git/.nozeli、依赖/生成输出及已知凭据文件；不跟随符号链接、外部路径或文档URL，不执行项目中嵌入指令，不使用扫描发现的凭据。到预算即生成部分地图并标coverage；排除规则降低意外泄露，不保证任意源码绝无秘密。自动初始化通过宿主有界能力约束，不仅靠YOLO模型提示词自律。
4. Orchestrator理解项目目标、目录职责、已有方案/报告、建议材料入口，生成一份简短项目地图和初始Plan Tree归属提议；不代用户 invent task、执行构建、改源文件、导入全部旧对话或自动把文件宣称verified。
5. 程序将一份可编辑地图写入既有`memory/plantree/topics/`并从根index关联，沿现有主题读取链可查；包含相对来源/章节/范围、可用digest/version及已看/排除/截断coverage，不复制全文、不提升为权限/真理。修订尊重用户纠正和并发CAS，旧实例晚到结果拒绝发布。运行状态留现有宿主记录，不另在Markdown维护任务账本。
6. 同一实例只一个初始化运行，重开从持久回执判断状态，失败不启动无限新会话。用户可继续整理，复用原project map修订，不不断复制MD。日常相关任务按需更新该主题，不每次打开全文扫描。

## 6. 实施切片与最小验收

先修正跨IPC保存责任并保留具体失败事实，再统一单协调者的保留/丢弃路径；随后接入自动有界恢复和首次语义初始化，不先建通用故障框架。

验收仅保留四条真实旅程：

1. 新建普通真实目录，模型启用后梳理文件→可读项目地图/来源；无模型仍打开阅读，冷开不重复推理。
2. 网页+对话+正文使用→普通关闭/重开；真实保存失败仍保护正文，不自锁保存请求。
3. 可自动处理的旧围栏/派生视图故障→程序/主控一次恢复→核验实际打开；无模型/未知效果不误报修复。
4. 故障不能恢复→明确确认完全重置→新实例冷开无旧状态/旧回调污染；原文件/Git/其他项目不变。停止不明、目录归属不明、磁盘失败仍明确阻断。

本草案未改变现有Orchestrator“路由为主”的生产职责；项目语义初始化和有界诊断是用户本轮要求的拟议职责扩展，正式实施时须同步角色合同和工具，不假装现有能力已接入。不得以此授权普遍自主改代码/命令或无限项目策展。

## 7. 独立Reviewer审阅与裁剪

首审needs changes，认可基本架构；要求五项澄清：AI启用后自动初始化而非重复审批；held项目直接可达重置；任务历史未知与活跃效果未知分开；中断重置必须安全结束或准确阻断；扫描预算和Plantree发布由宿主执行。以上已合入，不以“保存所有信息”为必须实现的复杂目标。

职责压缩为：**程序管安全与真实结果；Orchestrator管一次有界理解/诊断；用户只处理确实需要丢弃或外部前提的决定。** 不做自动修改安装代码、无限Debug、逐场景手修向导或第二存储/调度。

补充验收：AI不可用时本地打开正常，后续启用触发一次；含凭据/外链及超预算大目录生成诚实部分地图；地图必须经现有root-linked topic reader读回，用户纠正不被覆盖。其余沿§6四条旅程，不按每种故障扩展状态机。

最终复审：五项要求全部关闭，结论design-ready，无剩余设计阻断；单协调者、既有runtime/storage、四条真实旅程及定向断言足够，不再扩展场景目录或恢复框架。复审仅只读设计，不是实现/安装验收，也未解除当前用户项目围栏。
