## Runtime, dependency, platform, and edition distinctions

### Hindsight

Release README supports retain/recall/reflect; managed cloud is separate from self-hosted OSS. A TS client does not make the engine a JS embedded library. `hindsight-api-slim`/`hindsight-all[-slim]` require Python >=3.11; Python client >=3.10. PostgreSQL storage uses asyncpg, pgvector, SQLAlchemy/psycopg2; all-in-one pg0 is embedded **PostgreSQL**, not Nozeli's existing SQLite. README also advertises Oracle enterprise deployment; that is not an exercised OSS SQLite replacement. Native/transitive dependencies include greenlet, tokenizers, Rust-backed obstore, uvloop/non-Windows and winloop/Windows. Full/all extras and slim must not be conflated.

[Release installation source](https://github.com/vectorize-io/hindsight/blob/34a138684a899b6ec34175f7a2b633860466d289/hindsight-docs/docs/developer/installation.md) and README claim Linux x64/arm64, Apple Silicon, Windows x64 support; Intel macOS bare-metal uses slim caveat. This is upstream support, **not Nozeli three-platform verification**. Local Ollama/LMStudio/llamacpp providers are advertised, but extraction/reflection still require a configured model and embeddings; no model was downloaded or called. Docker quickstart is not an acceptable end-user prerequisite. Config has OTel tracing default false, but LLM request tracing default true/one-day retention; do not mistake disabled remote tracing for no sensitive local traces. No complete network-egress audit performed.

[Architecture implication] Useful retention/retrieval ideas, but adopting server, pg0, bank ownership, model extraction and a second DB would add packaging, stop/drain, purge and authority reconciliation obligations. It cannot authorize Work closure, knowledge approval, or truth.

Its “local” adjective does **not** establish no downloads, no model use, no port, or no native compilation/Electron ABI work. Learning, reflection and skill crystallization are intentional behaviors, contrary to Nozeli's default-off semantic postprocessing/explicit knowledge approval.

Telemetry sender source explicitly says enabled by default (`config.enabled !== false`), opt out via `telemetry.enabled: false`; actual sender disables if no configured ARMS endpoint/credentials. ### OpenViking v0.5.3 actual retrieval and breaking upgrades

[Pinned retrieval docs](https://github.com/volcengine/OpenViking/blob/178a8cdfb41b51e7d24c4bf79a13cc54981e0ee8/docs/en/concepts/07-retrieval.md) and `openviking/retrieve/hierarchical_retriever.py` agree: despite class name **HierarchicalRetriever, implementation is global vector retrieval**, with dense/sparse support and optional rerank, **not recursive tree navigation**. One global search/query is constrained by target dirs, context type, permissions, metadata filters and level; absent level, text can match L0/L1/L2 directly. Directory priority queues, parent→child score propagation and convergence rounds have been removed (docs line104). Hierarchical storage/summary presentation must not be advertised as current recursive retrieval algorithm.

QUICK/find recalls limit with no rerank; THINKING/search with usable reranker recalls 2×limit then one rerank pass to ≤limit; no usable reranker falls back to vector-only. Rerank works on recalled abstracts and never starts another search. Optional session-intent LLM planning is separate; search limit is per generated query and merged results can exceed it, with no guaranteed cross-query deduplication. Context mode uses find/vector scores unless explicit apply_rerank_to_context. All these are source semantics, not measured retrieval quality.

Saved official v0.5.3 release response lists incompatible changes: legacy `viking://session/...` URI removed/INVALID_URI, only user-scoped sessions read; migration admin endpoint returns400 and SDK/CLI migrate methods removed (old0.3.x deployments must migrate on older release first); group members switch to batch user_ids body; unknown roles/missing registration rejected. Companion SDK is0.1.18. These affect reproducibility/data recovery, not optional UI details. Existing Nozeli URIs/identity migration cannot be delegated to an engine's implicit backward compatibility.

### Hindsight-all npm launcher, scope, and history limits

Release-pinned [`hindsight-all-npm`](https://github.com/vectorize-io/hindsight/tree/34a138684a899b6ec34175f7a2b633860466d289/hindsight-all-npm) is Node>=22 **lifecycle wrapper**, not a Node memory engine or HTTP client. README requires uv/uvx on PATH; `src/command.ts` defaults to **`uvx hindsight-embed@latest`**, or developer local `uv run --directory ... hindsight-embed`. Pinning npm alone therefore does **not** pin the downloaded Python engine: embedVersion must be separately fixed. `server.ts` creates/merges profile, starts daemon and polls health; Python `daemon_embed_manager.py` resolves database to per-profile `pg0://hindsight-embed-<safe-profile>` unless explicit DB URL. Windows cold start comment documents pg0 initdb/unpack. Underlying Python API/interpreter, PostgreSQL/pg0, model and native dependencies remain, along with caches/profile/daemon ownership cleanup. No uv/daemon was run here.

[Pinned scope source](https://github.com/vectorize-io/hindsight/blob/34a138684a899b6ec34175f7a2b633860466d289/hindsight-api-slim/hindsight_api/engine/search/tags.py): default tags_match **any includes NULL/empty-tag memories**, all also includes untagged. `_strict` excludes untagged when tags supplied; empty tags normally means **no filter even in strict modes**. exact empty scope selects only global/untagged; exact nonempty requires set equality. Tags are retrieval semantics, **not tenant/project authorization**. A Nozeli adapter must bind bank/project and enforce owner/instance authorization independently; passing scope tags alone can widen to unrelated untagged/global content.

[Pinned document history source](https://github.com/vectorize-io/hindsight/blob/34a138684a899b6ec34175f7a2b633860466d289/hindsight-api-slim/hindsight_api/engine/document_history.py) explicitly documents limitations: observations are deleted/rebuilt; change events record **ids/counts, never text**, ID lists cap100; history rebuilt from async operation result_metadata bounded by operation retention. Synchronous retain and edits with auto-consolidation disabled can have no history event. Recording is **after commit/best-effort** and must not fail the change. Therefore document history is not durable immutable source-revision bytes or an atomic provenance/outbox guarantee; Nozeli frozen object digest/span and approval history remain host responsibilities. This is stronger evidence against substituting its history API than generic “has source provenance” claims.

### MemOS fixed main plugin runtime, deletion depth, and capture durability

Fixed main **`d326a6419467c2205041b58533b0ebfdf4f38173`** differs materially from server release tree. Main plugin engines **Node>=22.0.0**, native **better-sqlite3 exactly13.0.3**; `memory-core.ts:228-230` actively rejects actual host Node<22. Release plugin manifest had Node>=20 and better-sqlite3^12.10.0. Current native/release claims must remain separate; no Electron binary compatibility is inferred.

`memory-core.ts:3208-3241` deleteTrace/deleteTraces checks current ownership, transactionally removes trace ID from episode and deletes trace; optional hub unpublish happens **after local commit**, through hub-sync wrapper. Trace repo `deleteById:746-750` deletes trace FTS then trace row. It **does not traverse L2 policies, L3 world models, generated skill files, arbitrary summaries or dependent approvals**. Bulk deletion is explicitly one trace at a time, not all-or-nothing. `deletePolicy` is separate and similarly does not establish a recursive source revocation graph. Thus the observed API is not a Nozeli transitive lineage purge/tombstone gate; foreign-key side cleanup, where present, would still not prove semantic derivative invalidation.

Capture is not simply “all memory disappears on crash”: saved SQLite trace/episode rows survive process memory and main implements startup orphan/dirty-closed recovery, bounded scans/backoff, matching/dedup and embedding retry queue. But source does **not** justify exact-once durable capture/model calls: subscriber tracks pending Promises in a Set/fire-and-forget and logs failures; runLite summarizes/embeds **before** persistRows. `capture.ts:911-947` inserts rows one by one, queues missing vectors, then separately updates episode trace_ids; episode update failure becomes warning, not one shared transaction. Crash can fall between model completion, partial inserts, episode links and downstream `capture.done` reward/policy/skill events. Signature dedup and recovery mitigate some partials, not a durable claim/lease/outbox with provider-call receipt.

`memory-core.ts:722+` explicitly moves slow startup reflect/reward/L2 recovery into detached promise; shutdown cancellation/flush handling exists, so absence of recovery must not be alleged. It may still perform model work during startup recovery unless separately disabled/configured, conflicting with Nozeli no implicit model replay policy. DB connection defaults WAL+synchronous NORMAL; process-crash and power-loss durability are different, and neither was fault-injected here. Need actual kill barriers across capture→row→episode→reflection→policy/skill and recursive revoke/purge before adopting as authoritative knowledge. Do not declare safety from SQLite use or run exit0.

### Selection impact of the supplement

The assessment is **not** “all candidates are Python servers” or “none can run locally”: current Letta has Node local runtime; MemOS has TS local core; Mem0 TS persists vectors/history; LanceDB has embedded native Node binding. The decisive remaining delta is trustworthy project authority/explicit approval, immutable versioned source spans, atomic recoverable postprocessing, scoped reversible reads vs recursive revocation/purge, packaging and unknown-owner safety. Hindsight's default tag widening/history loss bounds, OpenViking's actual global-search semantics/upgrade removals, Mem0 v3's ADD-only/platform graph split and MemOS partial capture/deletion depth are material selection evidence. No candidate quality, native platform support or crash test was executed by this source audit.
